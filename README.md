# Спринт 6. Конверсия участников групп в первое сообщение

Проект загружает журнал событий групп из S3 в Vertica, расширяет слой DDS и рассчитывает конверсию для десяти старейших групп.

## Запуск

1. Откройте [Docker-тренажёр спринта](https://github.com/practicum-de/s6-lessons). Из папки `s6-lessons` запустите `docker compose up -d de-sprint-6`. Скопируйте `src/dags/sprint6_group_log.py` из проекта в папку `s6-lessons/dags`. Airflow доступен по адресу `http://localhost:3000/airflow`.
2. Настройте в Airflow переменную `sprint6_schema_prefix` со значением `VT261117917969` и подключение `sprint6_vertica` типа Generic. Используйте учебные реквизиты Vertica, имя базы `dwh` укажите в поле Schema. В DBeaver откройте соединение с этой же базой. Для другого учебного стенда замените префикс во всех SQL-файлах, в `scripts/load_base_staging.py` и в переменной Airflow. Схемы с суффиксами `__STAGING` и `__DWH` должны существовать.
3. Если базовые хабы и связи из предыдущих уроков отсутствуют, загрузите исходные данные. Из папки `s6-lessons` выполните команду ниже, подставив реальный путь к распакованному проекту. Скрипт загружает из публичного бакета `sprint6` поля, нужные для расчёта. Ожидается 170 000 пользователей, 250 групп и 1 037 747 сообщений. Затем выполните `src/sql/00_base_dds.sql` целиком в DBeaver. Если хабы и связи уже готовы, переходите к следующему шагу.

   ```bash
   docker compose exec -T de-sprint-6 python3 - < /путь/к/проекту/scripts/load_base_staging.py
   ```

4. В DBeaver в режиме **Auto** выполните `src/sql/01_create_tables.sql` через **Execute SQL Script**. Скрипт создаёт `group_log`, линк `l_user_group_activity` и сателлит `s_auth_history`.
5. В Airflow включите DAG `sprint6_group_log` и нажмите **Trigger DAG**. Дождитесь **Success** у задач скачивания и загрузки. CSV сохраняется в `dags/data`. Пустые `user_id_from` загружаются как SQL NULL в целочисленное поле.
6. В DBeaver выполните целиком `src/sql/02_load_dds.sql` через **Execute SQL Script** в режиме **Auto**. Скрипт создаёт связи пользователей с группами и переносит уникальные события. При повторном последовательном запуске пропускает существующие записи.
7. Выполните `src/sql/04_checks.sql`. Ожидается 889 733 строки в staging, 889 731 уникальное событие в DDS и 0 событий без соответствия хабам. Разницу дают два точных дубля `add`. В DDS ожидается 800 746 `add`, 250 `create` и 88 735 `leave`.
8. Выполните `src/sql/03_group_conversion.sql`. Для проверки CTE по отдельности можно заменить итоговый SELECT на `SELECT * FROM user_group_log;` или `SELECT * FROM user_group_messages;`, сохранив блок WITH.

## Методика и результат


Знаменатель — уникальные пользователи с событием `add` в группе. Числитель — вступившие пользователи, у которых найдено хотя бы одно сообщение в той же группе. Повторные вступления и сообщения не увеличивают счётчики. Событие `create` исключено из знаменателя согласно условию.

Итоговый запрос проверен в Vertica. В таблице ниже показан исходный `group_id`. SQL возвращает также `hk_group_id`. На этих данных отдельная проверка ограничения «сообщение в момент или после первого add» дала те же значения для всех десяти групп.
